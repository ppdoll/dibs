## D-01. 서비스 정체성

**Dibs (딥스)** — "call dibs = 먼저 찜하다".
BtoB(파트너 업체) + BtoC(일반 이용자)를 함께 다루는 **예약 오픈 플랫폼**.
프론트 UX 레퍼런스는 catchtable(app.catchtable.co.kr).

역할은 셋: **운영자(Admin)** / **파트너(Partner)** / **이용자(User)**.

---

## D-02. 이벤트 모드는 2개다

파트너가 이벤트를 만들 때 둘 중 하나를 고른다.

### 모드 A — 선착순 즉시확정 (INSTANT)

- **고정 금액**만 가능.
- 신청하는 순간 자리를 잡고, 유저는 **즉시 당락을 안다**.
- 정원 관리는 단일 원자적 조건부 UPDATE 하나로 처리
  (`SET claimedCount = claimedCount + 1 WHERE id = ? AND claimedCount < capacity`).
- 정원이 차거나 기간이 끝나면 마감.

### 모드 B — 금액 입찰형 (BID)

- min~max 범위에서 **원하는 금액**을 적어 신청 (min==max로 고정가도 가능, 0 ~ Int max).
- 기간 동안 **정원 초과로 얼마든지 받는다**. 신청은 단순 INSERT.
- 마감 후 파트너가 **순위 리스트를 보고 최종 명단을 확정/수정**한다.

---

## D-03. 정원 초과를 허용한다 ★

**결정**: 신청 단계에서 정원을 강제로 막지 않는다. 소폭 초과도 괜찮다.

**왜**: 최종 선택이 마감 후에 이루어지므로, 신청 시점에 정원을 지킬 이유가 없다.

**결과**: 이 프로젝트에서 가장 어려운 문제(서버리스 다중 인스턴스 환경의 경합 상태에서
정원 초과 방지)가 **통째로 사라졌다**. 분산 락, 원자적 카운터, 대기열 자동 승계 로직이
전부 불필요해졌다. 만료 반환 등으로 생기는 소폭 초과는 파트너가 최종 명단 화면에서 조정한다.

> 주의: 이것 때문에 **"선착순"은 더 이상 주 결정 기준이 아니다.** 실제 메커니즘은
> 마감이 있는 경매에 가깝다. 유저 대상 문구에서 이 점을 오해 없게 써야 한다.
> (모드 A만 진짜 선착순이다.)

---

## D-04. 순위 규칙 ★

```
1순위: 신청 금액 내림차순
2순위: 그 금액에 도달한 시각(lastBidAt) 오름차순
```

**동점 기준 시각은 "최초 신청시각"이 아니라 "그 금액에 도달한 시각"이다.**
8만원끼리 붙으면 8만원을 **먼저 부른** 사람이 이긴다.
표준 경매 규칙이고, 재입찰(D-06)과 앞뒤가 맞는다.

**순위 확정 시점 = 마감시각 + 디파짓 윈도우**.
마감 1분 전에 신청한 사람도 디파짓 10분을 온전히 쓸 수 있어야 하기 때문.

---

## D-05. 디파짓은 순위가 아니라 자격 요건이다 ★

- 신청 후 **10분 내에 금액의 일부를 디파짓**으로 내야 신청이 **유효**해진다.
  - 모드 A: 잡아둔 자리를 유지
  - 모드 B: 순위 집계에 포함
- 미납 시 만료 → 무효 (A는 자리 반환, B는 랭킹 제외).
- **순위를 정하는 금액은 "신청 금액"이지 "낸 디파짓 금액"이 아니다.**
  디파짓은 진지함을 증명하는 게이트일 뿐.
- 디파짓 설정은 **이벤트별**: 필수 여부 / 정액 or 정률(%) / 윈도우 분.
- 비선정자 디파짓은 환불한다.

**현재 범위**: 실제 결제(PG) 연동은 **후속 단계**.
지금은 상태·타이머·테이블 구조만 만들고 `DEPOSIT_HOLD_ENABLED=false`로 꺼둔다.

만료 처리는 서버리스라 상주 프로세스를 못 쓰므로 **Vercel Cron 스위퍼 + 조회 시 지연 만료(lazy expiry)** 조합.

---

## D-06. 재입찰은 올리기만 가능

- 금액 **상향만** 허용. 하향 불가, 취소 후 재신청으로 시각을 리셋하는 우회도 차단.
- 입찰 이력(BidHistory) 테이블에 전부 남긴다.
- 상향하면 `lastBidAt`이 그 시각으로 갱신된다 (D-04).
- **정률 디파짓이면 상향 시 차액이 생긴다.** 새 윈도우 안에 차액을 안 내면
  **직전(디파짓이 완납된) 금액으로 롤백**한다. 신청 자체는 유효하게 유지.
  → 올리기만 하고 안 내는 어뷰징 차단.

---

## D-07. 기간 중에는 경쟁률만 공개한다

- 공개: **`정원 10명 / 신청 47명 (4.7:1)`** 뿐.
- 비공개: 금액, 개인 순위, 커트라인. **자기 순위도 볼 수 없다** (밀봉입찰에 가깝다).
- 파트너와 운영자는 자기 이벤트의 금액·순위를 항상 전부 본다.

> **알려진 긴장**: 경쟁률만 공개 + 재입찰 허용(D-06)은 다소 어긋난다.
> 내 순위를 모르면 금액을 올릴 동기가 약하다.
> 일단 이대로 가되, 이벤트 설정에 **"커트라인 공개" / "내 순위 공개" 토글**의
> 자리를 미리 만들어 두고 나중에 켤 수 있게 한다.

---

## D-08. 마감 직전 스나이핑 대응 (소프트 클로즈)

금액이 1순위이므로 다들 마지막 순간에 넣으려 한다(먼저 넣으면 추월당하니까).
→ **이벤트별 옵션**으로, 마감 직전 N분 내에 신규/상향 입찰이 들어오면 마감을 N분 연장한다.

---

## D-09. 인증

- **구글 로그인만.** 가입 시 `일반 이용자` / `파트너` 선택.
- **파트너는 운영자 승인 후에야 활동 가능** (가입신청 → 승인/반려).
- 운영자 계정은 셀프가입 불가 — 시드/초대로만 생성.
- NestJS Passport(google) + JWT.

---

## D-10. 알림 채널

**앱 내 쪽지/알림 + 이메일(Resend)** 2개. 카카오 알림톡·SMS는 범위 밖(추후).

발송 트리거: 신청 완료 / 디파짓 요청(카운트다운) / 디파짓 확인 / 홀드 만료 /
재입찰 롤백 / 선정 / 미선정 / 이벤트 취소 / 마감 연장(소프트 클로즈).

- 운영자 → 세그먼트 브로드캐스트(전체 유저, 전체 파트너, 특정 이벤트 신청자)
- 파트너 → **자기 이벤트** 신청자에게만 (전체 / 상태별 필터)
- **알림 문구가 D-07의 비공개 정보(타인 금액·커트라인)를 흘리면 안 된다.**

## D-11. 기술 스택

| 영역 | 선택 |
|---|---|
| 호스팅 | Vercel |
| 모노레포 | Turborepo + pnpm |
| 프론트 | Next.js 15 App Router + Tailwind + shadcn/ui (`apps/web`) |
| 백엔드 | NestJS, Vercel 서버리스 함수로 배포 (`apps/api`) |
| 공용 | 타입/DTO/zod (`packages/shared`) |
| DB | Vercel Postgres (Neon) + Prisma |
| 이미지 | Vercel Blob |
| 이메일 | Resend |
| 만료 처리 | Vercel Cron |
| 실시간 경쟁률 | SSE / 폴링 (서버리스라 WebSocket 불가) |

**서버리스 제약**: 상주 프로세스 없음, WebSocket 불가, 콜드스타트 존재,
인스턴스 다중 실행. Prisma는 커넥션 풀링(pgbouncer / Neon pooler) 필수.
